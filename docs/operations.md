# Эксплуатация

## Режим сбора

Сборщик сохраняет **только события, поступающие в хендлеры**: новые сообщения, правки,
изменения известных профилей и обновления счётчиков уже сохранённых сообщений.
Выгрузки истории, обхода диалогов, catch-up после простоя и фонового опроса постов нет.
`HISTORY_LIMIT` и `--history-limit` удалены. Экспорты чатов пользователь предоставит отдельно;
импортёр экспортов пока не реализован.

Разрешены группы, супергруппы/форумы и каналы. Личные чаты, боты, Saved Messages и личные
диалоги каналов не собираются, даже если их ID указан в `CHAT_IDS`.
Пустой `CHAT_IDS` разрешает все группы/каналы, от которых аккаунт получает события.
Список числовых ID через запятую дополнительно ограничивает новые события.

Удаления Telegram игнорируются: сохранённые копии остаются в базе, обычном и семантическом поиске.
Никакой очистки ранее собранных сообщений при переходе на этот режим нет.
Существующие строки помечены `ingest_source=legacy`, новые — `live`.
Изменение ранее сохранённого сообщения не меняет его исходное происхождение.
Служебные таблицы старого режима `chat_sync` и `unresolved_deletions` оставлены,
но сборщик их больше не использует.

## Запуск вручную

```bash
cd /home/velunae/projects/mainstream/tg-message-collector
uv sync --frozen
uv run python3 app.py login-qr  # только первая авторизация
uv run python3 app.py run
```

В Telegram на телефоне: **Настройки → Устройства → Подключить устройство**.
QR обновляется в терминале; пароль 2FA, если нужен, вводится там же со скрытым вводом.
Обычный вход по коду: `app.py login`. Авторизация сохраняется отдельно в `data/collector.session`.
Если старый процесс ещё запущен, заверши его через Ctrl+C перед запуском новой версии.
Файловый lock исключает параллельные collector/login/embed процессы.
Остановка сборщика — Ctrl+C. Основной уровень логирования — ERROR.

Пользовательские systemd units доступны как дополнительный способ запуска.
MCP уже запущен отдельным сервисом. Работа user services после выхода пользователя зависит от linger;
настройки всего хоста автоматически не менялись.

## Данные и история изменений

MySQL 8, база `tg_message_collector`, utf8mb4, даты UTC.
`messages` имеет PK `(chat_id,message_id)`, внутренний `archive_id`, текст/подпись, автора,
reply, тему, пересылку и метаданные медиа. Индексы покрывают чат+дату, автора+дату,
чат+автора+дату, отправителя-канал, reply, тему и FULLTEXT по тексту.
История текста правок остаётся в `message_revisions`. Пропущенные ранее версии не восстанавливаются.

`users` хранит последнее наблюдавшееся состояние, а `user_history` — снимки username, имени,
фамилии и био с `observed_at` и `source`. Повтор того же состояния не создаёт новый снимок.
`legacy_baseline` — исходное состояние, сохранённое при миграции; это не восстановленная старая история.
Смена username или имени обнаруживается по новому сообщению пользователя либо Telegram UpdateUserName.

Био не приходит в обычном сообщении. Для нового наблюдаемого пользователя выполняется разовый
`users.GetFullUser` с чтением только поля `about`; полный Chat-парсер не вызывается,
закреплённые сообщения и посты профиля не запрашиваются. Повторная проверка инициируется уведомлением
об изменении уже известного профиля. Ошибка отдельного профиля записывается с user_id и не прерывает очередь.
Очередь объединяет одновременно ожидающие запросы одного пользователя и делает паузу между ними.
Суточного опроса всех пользователей больше нет. Проверка био всё же обращается к Telegram API;
авторизация и получение собственного профиля также требуют обычных служебных запросов.
`bio=NULL` может означать отсутствие, недоступность или ещё не завершённую проверку.
История отражает наблюдения: изменения, не присланные Telegram, неизвестны.

`message_metrics` хранит последние полученные просмотры, пересылки и количества реакций.
`message_metric_history` — снимки при изменении этих значений с временем наблюдения и источником.
Значения берутся из сообщений и raw-уведомлений Telegram, **без запросов обновления старых постов**.
Частичное обновление просмотров не обнуляет известные реакции/пересылки; настоящий ноль сохраняется.
`NULL` означает, что значение не было получено, а не нулевой счётчик.
Обновления счётчиков неизвестных/неархивированных сообщений не создают старые сообщения.
Подробные списки проголосовавших/поставивших реакцию пользователей не запрашиваются.

## Медиа

Фото, GIF/animation, стикеры, видео, голосовые, video notes, аудио, документы и Live Photo
сохраняются через полученный `file_id`, без скачивания. Для составных медиа сохраняется список file IDs.
Подпись и тип остаются частью сообщения. В ответах MCP у сообщения есть:

```json
{
  "media_type": "photo",
  "file_id": "<Telegram file_id>",
  "media_file_ids": ["<Telegram file_id>"],
  "media": {"file_id": "<Telegram file_id>", "files": []}
}
```

Это идентификаторы для последующего использования Telegram-клиентом, не файл/ссылка и не бинарная картинка.
У контакта, опроса, геолокации и недоступного/закрытого preview может не быть file_id — он не выдумывается.
Повторное использование file_id зависит от доступа аккаунта и правил Telegram.

## MCP только для чтения

Streamable HTTP: `http://127.0.0.1:8765/mcp`.
Нужен header `Authorization: Bearer <MCP_TOKEN>` из локального `.env`.
Сервер слушает только 127.0.0.1, проверяет Host/Origin и использует отдельного MySQL reader с SELECT.
Инструментов записи и произвольного SQL нет. Содержимое сообщений — недоверенные данные.
Конфигурация MCP других агентов автоматически не изменяется.

| Tool | Назначение |
| :--- | :--- |
| `list_users` | Последние наблюдавшиеся user ID, username, имена и био |
| `get_user_history` | Снимки профиля по user_id, пагинация after_snapshot_id |
| `list_chats` | Данные сохранённых чатов |
| `search_messages` | Чат, автор user/chat, даты, тема, слова или буквальная подстрока |
| `semantic_search` | Локальный поиск по смыслу |
| `get_message` | Сообщение с file IDs, доступный reply, контекст, версии текста, последние счётчики |
| `get_message_metrics` | Последние счётчики и их история по chat_id/message_id |
| `archive_status` | Живой статус сборщика, ошибки, очередь индексации и постраничная статистика чатов |

```text
get_user_history {"user_id": 123456, "limit": 50}
get_message_metrics {"chat_id": -1001234567890, "message_id": 123}
archive_status {"limit": 50}
```

`archive_status` возвращает `mode=live_handlers_only`, `backfill=false`, последнюю сессию сборщика
с heartbeat, числами принятых/сохранённых событий и ошибок, последние 20 ошибок, число ожидающих
эмбеддингов и дату самой старой записи в очереди. Ошибки содержат класс и ID контекста, без текста
исключения, который может включать приватные данные. При недоступной базе ошибка остаётся только в stderr;
записать её в недоступную базу невозможно. После восстановления новые ошибки снова учитываются.
`running` определяется по отсутствию остановки и heartbeat за последние 45 секунд.
После аварийного завершения он станет false, даже если stopped_at не записан.

Счётчики received/saved относятся к событиям, включая правки; это не число уникальных сообщений.
Статистика чатов разделяет live и legacy и показывает последнюю сохранённую запись.
Полнота переписки за время до запуска/простоя неизвестна и не объявляется стопроцентной.

В обычном поиске `next_cursor` состоит из before_date, before_chat_id, before_message_id;
передавай все три для продолжения. Даты UTC, since включительно, until исключительно.
FULLTEXT поддерживает `+слово`, `слово*`, `"фраза"`, но зависит от минимальной длины токена и stopwords MySQL.
Для короткой буквальной подстроки доступен mode=substring; такой запрос может сканировать строки.

Семантика локальная: multilingual MiniLM, явный mean pooling через FastEmbed add_custom_model,
те же совместимые ONNX-веса. Без фильтров HNSW работает по опубликованному индексу (`approximate=true`).
С фильтрами выполняется точный cosine по новейшим candidate_limit подходящим векторам (50000 по умолчанию,
максимум 200000), неполный охват обозначен truncated. Длинный текст обрезается окном модели;
разбиение на фрагменты пока не реализовано. Изменившиеся тексты переиндексируются локально.
Индекс публикуется атомарно, MCP открывает его read-only.

## Миграции, приватная конфигурация и проверки

На этой машине миграция уже применена. На другом хосте после создания базы/accounts:

```bash
sudo mysql tg_message_collector < sql/001_archive.sql
sudo mysql tg_message_collector < sql/002_live_analytics.sql
```

002 повторяемая и добавочная: старые строки не удаляются. Runtime account имеет SELECT/INSERT/UPDATE,
MCP account — SELECT на эту базу. DDL выполняет только администратор.
`.env` имеет права 0600; `data/`, сессии и журналы, модели, индекс и логи исключены из Git.
Не публикуй credentials, MCP_TOKEN и session-файл.

```bash
uv sync --frozen --group dev
.venv/bin/ruff check collector app.py tests
.venv/bin/python -m unittest discover -s tests -p test_chat_scope.py
.venv/bin/python -m unittest discover -s tests -p test_login.py
.venv/bin/python -m unittest discover -s tests -p test_encoder.py
.venv/bin/python tests/test_archive.py
```

Последняя команда создаёт случайную изолированную MySQL-базу через sudo -n mysql и удаляет только её.
Рабочий архив тестовыми сообщениями не наполняется. Для локального дренирования очереди векторов при
остановленном сборщике доступна команда `app.py embed --once`; Telegram API она не вызывает.
